# Notes for coding agents

- Expo SDK 58, React Native 0.88, React 19.3, expo-router with routes in `src/app`. Typed routes and the React Compiler are on. React Native's strict TypeScript API is on: type refs with instance types (`useRef<ScrollViewInstance>`, not `useRef<ScrollView>`), and don't deep-import from `react-native/Libraries`.
- The web build is one bundle (`asyncRoutes: { web: false }` in app.json): with split route files, a web app left open across a deploy would ask for files that no longer exist. `web.output` stays `single`.
- Navigation: every tab is a stack (`src/app/(tabs)/(fleet,review,people,table,log,me)/_layout.tsx`), so the tab bar stays on every page and detail pages (van, walk-around, check, person) open inside the current tab with a header and back button. Put new detail pages in that shared folder, not at the root. Only the camera (`scan/[id]`) sits at the root, full screen. Keep `(fleet)` sorting first alphabetically: links opened from outside land in the first group.
- Install native packages with `npx expo install <pkg>` so versions match the SDK. Without network access to the Expo API, prefix `EXPO_OFFLINE=1`.
- The app must keep working in Expo Go: no custom native code, no packages that need a development build.
- The same code is the App Store and Google Play app (Fratius, `com.fratius.app`, built by the Store build workflow; `STORE_BUILD=1` in app.config.js). Store apps get each Deploy's update only while their native packages match `store/native.json`: after adding or upgrading a native package, raise `version` in app.json, run `node scripts/native.mjs --write` and make new store builds (store/README.md). Modules Expo Go can't use (expo-notifications) load only outside Expo Go (`src/lib/nativepush.ts`, with a `.web.ts` stub).
- Uploads never ask anyone to take a photo or video again. Walk-around photos and videos go through the outbox (`src/lib/outbox.ts`, logic in `outboxcore.ts`, tested by `tests/outbox.test.mjs` in CI): kept on the phone first (`src/lib/keep.ts`: the documents folder, or IndexedDB on the web), then upload, walk-around record and server step, one job at a time, oldest first, each step retried by itself without a connection (also after the app was closed). Single photos in forms use `upload()` (lib/images.ts), which retries on its own; wrap the server call after it in `retrying()` (lib/net.ts) only when a repeat is safe. Any server step that can be repeated after a lost answer must answer the repeat as done (see `alreadyDone` in functions/src/index.ts, the purchase steps, `routineDone` with the phone's `id`), and `tests/history.test.mjs` checks the repeats. Storage only creates files, so a second upload of the same path is refused; `putBlob` then checks whether the file is there. With the React Compiler, screens read the outbox through `useOutbox()` (a fresh copy per change) and change it through `outbox`.
- Photos and videos are kept 30 days, damage 90 (`functions/src/media.ts` and `src/lib/media.ts` hold the same rule; change both). Records are never deleted; only files. People delete their own account with `deleteAccount` (ROLES.md).
- Test mode: build with `FLEET_TEST_MODE=1` (drops the Firebase config) and the app stores data on the device with AI checks off. Keep that path working; it's how the app is tested without a backend.
- The Anthropic key lives only in Secret Manager (`ANTHROPIC_API_KEY`), set by the Deploy workflow from the GitHub secret. Never put keys in the repo or the app.
- Model ids and prices are in two places: `functions/src/models.ts` and `src/lib/types.ts`. Change both.
- Before pushing: `npm run typecheck` and `npx expo export -p web`.
- Expo Go only opens one SDK. Match the SDK to the Expo Go version in the iOS App Store (check its version in Expo Go's settings), not to the newest SDK on npm: iOS Expo Go can lag weeks behind a release. Upgrade with `npm install expo@~NN` then `npx expo install --fix`.
- Roles: read `ROLES.md` before any change. App creator > fleet owner > fleet manager > driver; every feature respects it, enforced in rules, functions and screens. Joining is by one-time invite links (24 hours).
- Change `firestore.rules` together with `tests/rules.test.mjs`. Deploy stops if the rules tests fail.
- Van assignments and their history are permanent (ROLES.md, "Vans, drivers and history"): written only by Cloud Functions, never edited or deleted; one van per driver and one driver per van; vans are retired, not deleted. Drivers pick up and drop off vans only where the station allows it, and only with proof: the full photo set or a video (checked on the server; videos are converted with ffmpeg-static in the functions). `tests/history.test.mjs` checks all of it on the emulators; keep it passing.
- Fleet records: FLEET_DATA.md lists what is kept about vans and drivers, who sees what, and what is deliberately not stored. Business data (contracts, insurance terms) lives in `vehicleDetails`, never on the van document that drivers read; money lives in `vehicleCosts` (owners only), never in `vehicleDetails`. Tours, readings and the damage log are written only by Cloud Functions; licence checks too.
- Refuel, wash and parts: one callable `purchase` (actions start, dash, card, decide, receipt, finish, cancel, contacts) so it stays warm between the steps at the pump. Records in `purchases` are server-only and never deleted; card photos are deleted after reading and only the last 4 digits kept. The card is read by the quick model and anything but a clear match again by the stronger one before a driver is stopped. Flags (`purchaseFlags` in `functions/src/purchases.ts`) inform the manager and never block.
- The numbers in the Data tab come from `src/lib/stats.ts` (plain functions; keep the honest limits in its header true). The Excel file is written by `src/lib/xlsx.ts` without a library.
- Languages (src/lib/i18n.ts, src/lib/lang.tsx): every text people read goes through `t()`. The English text is the key; translations live in `public/i18n/<code>.json` (served with the web app; the phone app downloads and keeps them). Rules:
  - Whole sentences with `{placeholders}`: `t('Started {when} at {km}', { when, km })`. Never glue translated pieces into a sentence, never translate a string built with `${}`.
  - Counts: `tp(n, '{n} photo', '{n} photos')` (key = the English plural; each language has its own forms). A count inside a longer sentence: make the whole sentence the tp() text.
  - Text with styled parts inside a sentence: `tj('Card of {name} ...', { name: <B>…</B> })` inside a <Text>.
  - Constants at the top of a file (labels, option lists): wrap the English in `N_('...')` and translate where shown with `t(label)`. Never call `t()` at the top level of a file or in a constant: it runs once, in English.
  - Not translated: what people type, names (vans, stations, people, companies), plates, what the AI wrote (damage reasons, warnings it read), units like km, l, kWh, €, and technical names that stay as is (HU, UVV, AdBlue, VIN, Transporter ID, Expo Go, Excel, Firebase).
  - Dates and numbers: `toLocaleString(loc())` etc., never `undefined`.
  - Server messages: `fail(code, 'English with {x}', { x })` in the functions (the app translates it), notifications with `tr(lang, ...)`; texts stored in records for others to read (flags) carry their template and values so each reader sees their own language.
  - One English text, one meaning: the same word used for two things (a van's right side and "the AI was right") gets two keys ("Right", "Correct"), because other languages need two words.
  - After adding texts: `node scripts/i18n.mjs` lists them (i18n/keys.json, and i18n/source.txt with a short id per text) and what each language misses; missing ones show in English until translated. CI fails when a translation loses or invents a `{placeholder}`.
  - Translating (31 languages, AI-made, not yet checked by native speakers): follow i18n/GLOSSARY.md; write `{"id","t"}` lines to i18n/out/<code>.*.jsonl (not committed) and run `node scripts/i18n-merge.mjs <code>`, which writes public/i18n/<code>.json and checks it. Plural forms per language: scripts/plural-forms.mjs.
  - Right-to-left (Arabic, Persian): the web app flips (html dir); arrows use `fwd()` / `back()`. The phone app keeps the left-to-right layout (switching it needs a restart of the app), only the text is right-to-left.
  - Fonts: Barlow has Latin letters only; on the web the font names carry a sans-serif fallback (`F` in ui.tsx) so Cyrillic, Greek, Arabic and Devanagari don't fall back to a serif.
  - Functions are compiled to CommonJS, which doesn't hoist imports: import './i18n' before any top-level `N_()`.
- Website (fratius.com): plain files in `website/` (index, impressum, datenschutz, 404, fonts, icons), deployed by the Deploy workflow as the Hosting target `website` (site `fratius-web`, or the WEBSITE_SITE variable); the app is the target `app`. No requests to other hosts: fonts are served from `website/fonts` (Barlow, OFL), and the CSP in firebase.json only allows the site itself. Settings (prices, store links, legal links) are the `CONFIG` object at the top of the page's script. Prices are shown only in the pricing section; plans go by vans (any number of stations), and the sign-up form picks the plan from the vans (or the pricing card used). Languages: the page translates itself in the browser into the same 32 languages as the app (`?lang=`, then the visitor's earlier choice, then the browser's languages, else English; switcher in the header: their language, English, all languages). Every text node and label of the body is a key, plus `t()`/`N_()` in the script; mark names, plates and other example data `translate="no"`. After changing texts run `node scripts/site-i18n.mjs` (writes i18n/site-keys.json, lists what each language misses), translate per i18n/SITE.md into `website/i18n/<code>.json`; new texts show in English until translated (CI warns), and CI fails when a translation loses or invents a `{placeholder}`. The legal pages stay German/English (binding versions). The request form posts to `/api/signup`, a Hosting rewrite to the `websiteSignup` function (functions/src/website.ts checks the input): requests go to `siteRequests`, spam counters to `siteLimits`, both server-only (no rule lets an app user in; tests in rules.test.mjs and history.test.mjs). It emails info@fratius.com when the `SMTP_URL` secret is set (GitHub secret, copied to Secret Manager by Deploy; "none" otherwise) and notifies the app creator. The Impressum and privacy policy mark missing company details with `<mark class="todo">`; Deploy warns while any are left.
